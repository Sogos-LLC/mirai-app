Course Generation Documentation

Technical documentation for the AI-powered course generation system

System Overview

Mirai's course generation system uses a hierarchical, multi-phase approach to transform user inputs (course goals, SME knowledge, target audience) into complete, structured course content. The system is built on a strict contract architecture where Protocol Buffers define all data structures, and SQL migrations define persistence.

Core Architecture Principles

  • Single Source of Truth (SSOT): Proto files define all contracts, SQL defines all schemas
  • Schema-First Development: Define interfaces before implementing business logic
  • Compile-Time Safety: Build failures over runtime errors via generated types
  • Multi-Tenant Security: Every query is tenant-scoped via Row-Level Security (RLS)

Input Parameters

The generation system accepts rich, structured inputs that provide context for AI-generated content. These inputs are defined in proto/mirai/v1/ai_generation.proto.

Course Configuration

  • Course Title: The name of the course being generated
  • Desired Outcome: What learners should be able to do after completing the course
  • Additional Context: Extra instructions or constraints for generation

SME Knowledge

Subject Matter Expert (SME) knowledge provides domain expertise for course content:

  • SME Name: Name of the expert source
  • Domain: Area of expertise
  • Summary: Overview of the expert's knowledge
  • Chunks: Discrete pieces of knowledge (limited to 5 per call to manage context)
  • Keywords: Combined topics and tags for the domain

Target Audience

Audience profiling ensures content is appropriately tailored:

  • Role: Job title or function (e.g., "Software Developer")
  • Experience Level: Beginner, intermediate, advanced
  • Learning Goals: What the audience wants to achieve
  • Prerequisites: Required prior knowledge
  • Challenges: Pain points the course should address
  • Motivations: Why they're taking the course
  • Industry Context: Relevant industry or domain
  • Typical Background: Common educational/professional background

Phase 1: Outline Generation

Outline generation creates the course structure: sections and lessons with learning objectives. It uses a two-call approach to work around Gemini's JSON schema depth limitations.

Why Two Calls? Gemini's structured output has limitations on schema nesting depth. By first generating sections with lesson titles (flat), then expanding each section's lessons in parallel, we avoid hitting these limits while maintaining rich output structure.

Call 1: Generate Sections with Lesson Titles

1

Build Prompt

buildSectionsOnlyPrompt() constructs a prompt with: role statement, course info, target audience profile, SME knowledge (limited chunks), and instructions for generating sections with lesson titles.

2

Call Gemini API

Uses sectionsOnlySchema() - a flat JSON schema that returns sections with titles, descriptions, and lesson titles (no nested lesson details).

3

Parse Response

Extracts section structure and lesson titles. Each section becomes a unit for parallel expansion in the next phase.

Calls 2-N: Parallel Section Expansion

4

Build Section Prompts

For each section, buildSectionLessonsPrompt() creates a focused prompt with section context, lesson titles to expand, and audience info.

5

Parallel Gemini Calls

All section expansions run in parallel (rate-limited at 2000 RPM). Each call uses sectionLessonsSchema() to generate: lesson titles, descriptions, durations (5-20 min), and 2-4 learning objectives.

6

Merge and Compute Position Flags

All expanded sections are merged. Position flags are computed: IsFirstInCourse, IsLastInCourse, IsFirstInSection, IsLastInSection. These flags inform component generation later.

7

Store in MinIO

The complete outline is stored atomically in the course content JSON at tenants/{tenantID}/courses/{courseID}/content.json.

Output Structure

The generated outline contains:

  • Sections: Title, description, order, UUID
  • Lessons: Title, description, duration, learning objectives, position flags, UUID

Phase 2: Lesson Content Generation

After outline approval, lesson content generation creates the actual learning materials. Each lesson is generated through a three-phase process with context accumulation.

Job Architecture

Lesson generation uses a hierarchical job model:

  • Parent Job (FULL_COURSE): Tracks overall progress, created in PROCESSING state
  • Child Jobs (LESSON_CONTENT): One per lesson, run in parallel, linked via parent_job_id

Atomic Parent Finalization: The last child job to complete atomically finalizes the parent using FOR UPDATE locking. This prevents race conditions when multiple workers complete simultaneously.

Per-Lesson Generation: Three Phases

Phase A: Component Planning

A1

Build Planning Prompt

buildComponentPlanPrompt() creates a rich context including: course overview, full outline with current position markers, section/lesson context, learning objectives, previously completed lessons, navigation context, and target audience.

A2

Generate Component Plan

Gemini generates 5-8 component types with purposes. Each component type is planned with a specific role in the lesson flow.

Phase B: Iterative Component Generation

B1

Build Component Prompt with Position Context

buildSingleComponentPromptWithPosition() includes: course/section/lesson context, position flags, learning objectives, component type to generate, and previous components context (accumulated summaries).

B2

Generate Single Component

Gemini generates one component at a time. This ensures each component is aware of what came before, creating coherent flow.

B3

Parse and Transform

parseAndTransformComponent() converts the AI output to the appropriate component structure (TEXT, HEADING, QUIZ, etc.).

B4

Accumulate Context

The generated component's summary is added to previousComponentsContext. This context is passed to the next iteration, building up lesson coherence.

Phase C: Segue Generation

C1

Determine Segue Type

Based on position flags, the system determines the appropriate segue:

  • LESSON_TO_LESSON: 1-2 sentence transition to next lesson
  • SECTION_TO_SECTION: Preview of next section with excitement
  • COURSE_CONCLUSION: Congratulations, summary, next steps
C2

Generate Segue Text

buildSeguePrompt() creates position-appropriate transition text that guides learners to the next content.

Background Job System

The generation system uses Asynq (Redis-backed) for reliable background processing with automatic retry, crash recovery, and horizontal scaling support.

Job Types

Type Purpose Behavior
COURSE_OUTLINE Generate course outline Single job, user-triggered
FULL_COURSE Parent job for lesson batch Tracks children, finalized atomically
LESSON_CONTENT Generate single lesson Child of FULL_COURSE, runs in parallel
COMPONENT_REGEN Regenerate single component On-demand, user-triggered

Job Statuses

  • QUEUED: Waiting to be claimed by a worker
  • PROCESSING: Being actively worked on
  • COMPLETED: Successfully finished
  • FAILED: Encountered an error
  • CANCELLED: Cancelled by user

Atomic Job Claiming

Workers claim jobs using SELECT FOR UPDATE SKIP LOCKED:

-- Atomic claim prevents thundering herd UPDATE generation_jobs SET status = 'processing', started_at = NOW() WHERE id = ( SELECT id FROM generation_jobs WHERE status IN ('queued', 'processing') AND (status = 'queued' OR started_at < NOW() - '30 minutes'::interval) LIMIT 1 FOR UPDATE SKIP LOCKED ) RETURNING *;

Jobs stuck in PROCESSING for >30 minutes are considered crashed and can be reclaimed.

Parent-Child Job Tracking

Child jobs reference their parent via parent_job_id. When a child completes:

  1. Child job status updated to COMPLETED
  2. checkAndCompleteParentJob() called
  3. Child stats aggregated (completed, failed, pending counts)
  4. If all children done, parent atomically finalized with FOR UPDATE lock
  5. Parent job event published

Real-time Event Streaming

The system uses Server-Sent Events (SSE) via Connect-RPC streaming instead of polling. This provides instant updates with lower network overhead.

Architecture

  • Publisher: Backend services publish job events to Redis pub/sub
  • Channel: events:jobs:{userID}
  • Subscriber: SubscribeJobs RPC handler
  • Client: Frontend establishes persistent SSE connection

Event Types

Event When Published
JOB_EVENT_TYPE_CREATED Job added to queue
JOB_EVENT_TYPE_UPDATED Progress or status changed
JOB_EVENT_TYPE_COMPLETED Job finished successfully
JOB_EVENT_TYPE_FAILED Job encountered error
JOB_EVENT_TYPE_CANCELLED User cancelled job
JOB_EVENT_TYPE_KEEPALIVE Every 15 seconds (prevents proxy timeout)

Keepalive Requirement: The 15-second heartbeat prevents proxy timeouts (Cloudflare defaults to ~30s). Without keepalives, long-running connections would be dropped.

Rate Limiting and Error Handling

The Gemini integration includes robust rate limiting and retry logic.

Rate Limit Configuration

  • Max RPM: 2000 requests per minute
  • Burst: 100 concurrent requests
  • Base Delay: 30ms between requests (~33 tokens/second)
  • Max Retries: 3 for rate limit errors

Exponential Backoff

When receiving 429 (Rate Limited) or ResourceExhausted errors:

  • Retry 1: Wait 6 seconds
  • Retry 2: Wait 12 seconds
  • Retry 3: Wait 24 seconds
  • After 3 retries: Return error to caller

Content Storage

All generated content is stored in MinIO (S3-compatible), not PostgreSQL. PostgreSQL is used only for job tracking and tenant configuration.

Storage Structure

tenants/{tenantID}/courses/{courseID}/ ├── content.json # Course outline + settings ├── generated_lessons/ # All lesson content │ ├── {lessonID}.json │ └── ... └── images/ # Generated images ├── {imageID}.png └── ...

Optimistic Concurrency

All writes use optimistic concurrency control to prevent race conditions. Version numbers are checked before updates, and writes fail if the version changed.
